# ADR-0039: Screens approved before code (the design gate)

Date: 2026-10-11 · Status: accepted

## Context

On 05/10 the founder asked for the front-end to be validated before any code is written:

- send references;
- have the front-end ask questions;
- involve a UX role;
- approve the screens before coding.

Figma was suggested, open to a better proposal. The factories showed why:

- the Worker moved a sprite 1 px to pass the smoke;
- nobody looks at the screenshots of ADR-0030, because the visual check is geometry only, with no
  right picture to compare against.

The plan (Phase 15) recorded why Figma is not the main path:

- only clients in Figma's MCP catalog may write to the canvas;
- the per-plan read limits are tight;
- it needs a Figma account and practice;
- it does not run in the dry run;
- one more translation from drawing to code is where the result drifts.

## Decision

### 1. The UX Loompa (`agents/ux.py`, role `ux`)

- **Tool profile.** It reads the repository and memory (`design` documents included) and writes
  only under `.loompa/design/` (`toolbox.PROFILES["ux"]`). In practice code writes its files from
  its JSON answer, so a screen can never land elsewhere.
- **Cluster.** `engineering`: it writes HTML and CSS.
- **Prompts.** Five, English, product-agnostic, with the dry-run markers:
  - `Propose the visual base`;
  - `front-end questions`;
  - `Draw the screens`;
  - `Look at the pictures`;
  - built page vs approved screen.

  They entered without the bench: a new role has no recorded cases (plan, reminders).
- **Vision.** `Message.images` (data URLs) are sent as OpenAI `image_url` parts and Anthropic
  `image` blocks. `models.vision` lists the models a call with pictures goes to first. When it is
  empty, the looking steps are skipped and noted, and every check in code still runs.

### 2. Where the gate sits

The route is:

    intake → spec → spec_review → design → design_review → plan → …

The Master's classification gained `screen` (the story changes what a person sees). The gate
applies only when all three hold:

- `screen` is true;
- the product has a screen (`has_screen`: a front-end framework in the stack, a front-end file
  in the repository, or a chosen visual base);
- the gate is on.

A command-line tool never passes, whatever a story says.

The mode is `design.gate`:

| Setting | Meaning |
|---|---|
| `auto` (default) | follows the factory's kind (16.1, `factory_kind.design_gate`): `full` on a commercial product, `light` on a personal one |
| `full` | every screen the story adds or changes, the states the spec asks for, and two alternatives for the first screen of an epic that has no approved screen yet |
| `light` | one screen, its main state |
| `off` | no gate |

### 3. The visual base, once per factory

The first story that reaches `design` with no base gets two alternatives from the UX:

- tokens (colour, font, space, radius, shadow);
- a style board in HTML.

Both are photographed at 1280 and 390 px, and the contrast of the pairs the base promises is
measured in code (WCAG 4.5:1). The founder picks one, or asks for another round with notes.

The pick is written to:

- `design/tokens.json` and `tokens.css` (CSS custom properties, generated by code);
- a `## Front-end` section of the constitution, with the rules of 15.7.

Another story reaching `design` meanwhile parks (`waiting.design_base`). It resumes once the base
exists, so there is only one proposal and one question.

### 4. Questions, then screens, checked before anyone sees them

- **Questions.** Once per story, the UX lists the front-end questions the spec, the company
  documents, the base and the references do not answer. They go to the founder as **one
  decision with several questions** (`FounderMessage.questions`, answered in
  `FounderAnswer.answers`), each with a recommended option. With no question, there is no wait.
- **Screens.** Each screen state is a static HTML page:
  - the tokens are injected by code and scripts are stripped;
  - it is photographed at both widths;
  - it is checked in code:
    - every criterion points to a screen or is declared not visible (full mode);
    - no colour outside the tokens;
    - no sideways scroll and no element sticking out (the smoke's probes);
    - no serious or critical axe-core fault (axe-core 4.10.3, MPL-2.0, vendored as
      `design/axe.min.js`).
  - With a vision model, the UX also looks at its own pictures.
- **Retries.** What fails goes back to the UX, at most three tries (the founder's rule of three
  attempts). What still fails after that travels to the founder with the screens.

### 5. Approval, the contract

`design_review` sends one decision with:

- the pictures;
- a link to each static page (served with a sandboxing CSP);
- the UX's assumptions;
- the options:
  - approve;
  - approve alternative A or B;
  - approve with a Figma frame in place of the main screen;
  - ask for adjustments, with a note per screen.

An adjustment is a new round. From the third round on, the message says how many there were.

The approved round is copied to `design/S-0XX/approved/`. Its HTML goes, as data, into the
Architect's and the Worker's prompts (`approved_html`). A change after approval is a new round,
never an adjustment hidden in the code.

### 6. The built page against the approved screen (15.6, 15.7)

The Inspector runs `design.check` on every story once the factory has a base:

- **Colours.** A colour added to a style file or page template that is not a token fails the
  story. Scripts are left out: a game draws sprites with colours in code.
- **Pictures.** For each approved screen with a route, the product is started with the smoke's
  command (`smoke.served`) and the route is photographed at both widths. Each picture is compared
  in code with the approved one: both are shrunk to 160 px of grey, and the score is the share of
  pixels that moved more than 48 levels. Past `design.diff_threshold` (0.12), the UX looks at the
  two side by side with the front-end diff and answers:
  - `deviation` or `workaround` (layout or data bent only to pass a check, 15.7) fails the story,
    with the side-by-side picture in the delivery's pictures;
  - a difference nobody could judge (no vision model) is a finding for the founder.
- **Accessibility.** axe-core faults on those pages are findings.

### 7. References (15.2) and Figma (15.9)

A reference belongs to the product or to one story, and is one of:

- a picture;
- a site, photographed in the headless browser when added;
- a Figma frame;
- words.

They are kept in `design/references/` and indexed in memory as `design`. The UX reads them as
material, never as instructions, and with a vision model it also sees up to three pictures.

A Figma frame is read through the REST API with a personal token, which is kept in the secrets
files and never written to Figma. The frame's picture and outline become a reference, and the
approval can use it as the approved picture of the main screen. Writing to Figma stays out until
the Loompa's client is in Figma's MCP catalog.

### 8. The panel

- **🎨 Design**, with four tabs:
  - the approvals waiting, together, which is the batch at the start of a sprint;
  - the visual base;
  - the references, with upload, link, Figma and text;
  - each story's rounds.
- **The inbox** renders a decision's questions and screens.
- **The story drawer** links to the story's screens.
- **The settings' "Fábrica" tab** sets the gate, the vision models and the Figma token.
- **The UX** joined the brainstorm's consultants (15.8).

## Consequences

- A story with a screen costs a few more calls (questions, screens, a look) and waits for one
  approval. Approvals arrive together at the start of a sprint, because every story runs spec →
  design in parallel.
- The visual check now has a right picture. Example data never matches real data, so the
  comparison in code is coarse on purpose, and the judgement is the vision model's.
- Without a vision model the gate still works: screens, code checks and the founder's eyes.
- Files under `design/*/round-*/` and `design/base/` stay out of git (`.gitignore`); the approved
  rounds, the tokens, the board and the references are the factory's records.

## Not done, on purpose

- **Lighthouse.** axe-core covers the accessibility half. Performance belongs to the code, not to
  static screens.
- **States other than the main one in the visual comparison.** Reproducing an empty or error state
  in the running product needs data the factory does not control.
- **Writing to Figma.**
- **A bench run for the UX prompts.** It comes on the first real calls, as the plan says for a new
  role.
